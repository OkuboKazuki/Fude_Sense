【項目 ⑤】UI「PNG保存」表記と実装（BMP・デスクトップ直書き）の乖離
--------------------------------------------------------------------------------
■ 現状の課題:
  - 左メニュー「保存」タブのボタンには「🖼️ 作品画像を保存 (PNG)」と表示されているが、
    実際に出力されるファイルは無圧縮の 24bit BMP 形式 (.bmp)。
  - また、ファイルの保存先が「デスクトップ直下（日時ファイル名）」に固定されており、
    ユーザーがフォルダやファイル名を指定するダイアログが出ない。

■ 該当箇所:
  - App/SampleCode/Views/FloatingMenuView.cpp (L110)
  - App/SampleCode/Services/ImageExporter.cpp (L39-L75)
  - App/SampleCode/Controllers/AppController.cpp (L433-L436)

■ 判断が必要な理由:
  PNGエンコーダを実装するか、表記をBMPに合わせて工数を抑えるか。
  また、手軽な「ワンクリックでデスクトップ保存」を意図したUXなのか、
  標準的な「名前を付けて保存」ダイアログを出すべきかの設計判断が必要。

■ 選択肢:
  【案A】 WIC (Windows Imaging Component) を用いて本物の PNG 保存を実装する（推奨）
    - メリット: UIの表記と完全に一致し、ファイルサイズも大幅に削減（数MB→数百KB）。
    - 実装内容: COM / WIC (IWICImagingFactory) を用いてビットマップを PNG エンコード。
    - 工数: 約1時間。

  【案B】 UIの表記を「🖼️ 作品画像を保存 (BMP)」に変更する
    - メリット: 既存のBMP出力コードをそのまま流用でき、工数が最小（数分）。
    - デメリット: 審査員から「なぜ2020年代に未圧縮BMPなのか？」と突っ込まれる可能性。

  【保存先ダイアログの要否】
    - ダイアログあり: GetSaveFileNameW で保存先を指定（JSON/CSV保存と同様の挙動に統一）。
    - ワンクリック維持: 現在の「デスクトップに即時保存」＋トースト通知を維持。

  答え : 案Aで

【項目 ⑦】GPUコンピュートシェーダー実行時の「GPU-CPU-GPU ピンポン転送」ボトルネック
--------------------------------------------------------------------------------
■ 現状の課題:
  - Direct3D 11 Compute Shader (GpuSimulator) で物理にじみ計算を行うパスがあるが、
    1ステップ計算するごとに GPU テクスチャから CPU 側バッファへ全ピクセルを
    同期リードバック (Map/Unmap) し、それをさらに Direct2D の CopyFromMemory で
    Direct2D 側テクスチャへ送り直している。
  - GPU の高い並列演算性能が、PCIe バスの帯域消費と CPU-GPU 同期待機（ストール）
    によって相殺されている。

■ 該当箇所:
  - App/SampleCode/InkEngine/GpuInk.cpp (L584-L588, L1100-L1115)
  - App/SampleCode/InkEngine/GpuSimulator.cpp (L420-L460)

■ 判断が必要な理由:
  ゼロコピー（GPU内完結）に移行する場合、Direct2D と Direct3D 11 のテクスチャ共有
  (CreateBitmapFromDxgiSurface) が必要となるが、以下の機能との兼ね合いがある:
  1. 「一画戻す (Undo)」機能が CPU 上の RLE 圧縮スナップショットに依存している。
  2. CPU セルラー・オートマトン フォールバックとのデータ整合性。

■ 選択肢:
  【案A】 DXGI サーフェス共有によるゼロコピー完全 GPU パイプライン化
    - メリット: GPU内で直接描画ビットマップへ更新されるため、転送負荷が完全消滅。
    - デメリット: Undoスナップショットの取得タイミングやリサイズ処理の再設計が必要。
    - 工数: 約3〜5時間（大規模改修）。

  【案B】 非同期ステージングリードバック（Triple Buffering）または局所転送
    - メリット: 全画面転送ではなく、Dirty Rect（更新領域のみ）のリードバックに留めるか、
      直前のフレームを非同期に読み出すことでパイプラインストールを軽減。
    - 工数: 約2時間。

  【案C】 現状のハイブリッド構造を維持し、設計ドキュメントで説明する
    - メリット: コードを変更せず、現在の安定性を維持。
    - 対策: 「リアルタイム運筆レスポンス（低遅延）と Undo 用スナップショット生成の
      両立のため、現在は同期リードバックを採用している」と審査員向けドキュメントに明記。

  答え : 案Bで対応。

【項目 ⑨】GDI と Direct2D が混在したキメラ描画アーキテクチャ
--------------------------------------------------------------------------------
■ 現状の課題:
  - 画面全体のバックバッファ管理が GDI (CreateCompatibleDC / BitBlt) で行われており、
    半紙の墨汁描画部分のみ Direct2D (ID2D1DCRenderTarget) をバインドして描画している。
  - レガシー Win32 GDI と モダンな Direct2D が混在しており、描画パイプラインの
    ハードウェアアクセラレーションを100%活かしきれていない。

■ 該当箇所:
  - App/SampleCode/Views/MainView.cpp (L15-L105)
  - App/SampleCode/Views/CanvasView.cpp (L380-L382)
  - App/SampleCode/InkEngine/GpuInk.cpp (L1120-L1133)

■ 判断が必要な理由:
  UIウィジェット（ボタン、スライダー、木製机背景など）をすべて Direct2D / DirectWrite
  に移行するか、現行の GDI + D2D ハイブリッドを維持するかの基本方針決定。

■ 選択肢:
  【案A】 現行の「UI=GDI, 墨汁=D2D」ハイブリッドを維持し、設計書で正当化する（推奨）
    - 理由: 現在の UI は RenderUtils 等で高度に完成しており、フリッカーもなく
      軽快に動作している。全 UI を Direct2D に書き直す工数は膨大（数十時間）。
    - 対策: 「軽量・高互換な GDI UI と、物理演算テクスチャに特化した Direct2D の
      責務分離アーキテクチャ」としてドキュメント（README / 設計書）で説明する。

  【案B】 Direct2D 1.1 (ID2D1DeviceContext / DirectWrite) への完全移行
    - メリット: 全描画が GPU 完結となり、フォント描画（DirectWrite）やアルファ合成が
      極めて高速・高品質になる。
    - デメリット: 全 View クラス（FloatingMenu, InkStone, CanvasView, Modal）の全面刷新が必要。
  答え : 案Aで対応

【項目 ⑩】グローバル変数の乱立と神オブジェクト化 (AppState)
--------------------------------------------------------------------------------
■ 現状の課題:
  - WacomMT_Scribble.cpp に g_appState, g_gpuInk, g_strokeCtrl, g_appCtrl, g_wintab
    が静的グローバル変数として配置されている。
  - AppState が UI ウィジェットの全矩形・状態、筆・紙・お手本設定、物理モデル、
    セッション記録、履歴、キャリブレーションまで全てを抱える「God Object」になっている。

■ 該当箇所:
  - App/SampleCode/WacomMT_Scribble.cpp (L48-L62)
  - App/SampleCode/Models/AppState.h (L237-L265)

■ 判断が必要な理由:
  オブジェクト指向・現代的 C++ 設計（クリーンアーキテクチャ）へのリファクタリング方針。
  コンテスト審査では「単一責任の原則（SRP）」が問われることがある。

■ 選択肢:
  【案A】 AppContext / FudeSenseApp クラスの導入と HWND (GWLP_USERDATA) への集約
    - メリット: グローバル変数を完全に排除し、Win32 の正統な設計に統一。
    - 実装内容: アプリケーション状態を一元管理するクラスを作成し、WM_CREATE で
      SetWindowLongPtr(hWnd, GWLP_USERDATA, ...) して WndProc で取り出す。
    - 工数: 約1.5時間。

  【案B】 AppState の責務分割
    - メリット: UIState（ビュー用状態）と DocumentState（揮毫データ・設定）を明確に分離。
    - 工数: 約2時間。

  【案C】 現状維持（コメントとモジュール構成図の拡充）
    - メリット: 動作への影響リスクがゼロ。
    - 対策: AGENTS.md や README に「各サブシステム（Models/Views/Controllers）の
      ハブとして AppState を意図的にファサード配置している」旨を記載。

  答え : 案c

【項目 ⑫】高DPI（Per-Monitor DPI V2）/ 4K環境での描画ぼやけ・座標ズレ
--------------------------------------------------------------------------------
■ 現状の課題:
  - Direct2D レンダーターゲットの DPI が 96.0f (SetDpi(96.0f, 96.0f)) に固定されている。
  - 高解像度ディスプレイ（Surface Pro や 4K 液タブなど、スケール 150%〜200%）で
    実行した場合、OS のスケーリングによって文字や線がぼやけたり、
    ペン座標と描画位置にオフセットが生じるリスクがある。

■ 該当箇所:
  - App/SampleCode/InkEngine/GpuInk.cpp (L1125)
  - App/SampleCode/FudeSense.vcxproj (マニフェスト設定)

■ 判断が必要な理由:
  Per-Monitor V2 を有効にすると、ウィンドウリサイズやマルチモニタ移動時に
  フォントサイズやUI矩形（Layout）のスケール再計算が必要となる。

■ 選択肢:
  【案A】 マニフェストで DPI-Aware (Per-Monitor V2) を有効化し、動的スケール対応
    - メリット: 4K 液タブや Surface 環境で極めてシャープな表示と正確な運筆が可能。
    - 実装内容: GetDpiForWindow を取得し、DPI スケール係数 (dpi / 96.0) を
      AppState::Layout や RenderUtils::CreateCustomFont に乗算する。
    - 工数: 約2〜3時間。

  【案B】 マニフェストで GDI スケーリング (gdiScaling) を有効化する
    - メリット: コード側の修正をほとんど行わずに、OS 側で GDI プリミティブを高解像度
      レンダリングさせ、文字の滲みを防止できる（Windows 10 1703 以降の機能）。
    - 工数: 約15分（マニフェスト追記のみ）。

  答え : 案Bを試行したところ、OS側のスケーリング介入によりフローティングメニューの
         寸法変化およびWintab/Pointerペン入力の座標ズレが発生したため、
         元の PerMonitorHighDPIAware（1:1物理ピクセル完全対応）へ復元・維持。
