# Fude Sense ドキュメント同期

Fude Sense のドキュメントは 3 種類あり、読み手が違う。コードが変わったら、その変更が**どの読み手にとって意味があるか**で直す場所を決める。

| ファイル | 読み手 | 書いてあること |
|---|---|---|
| `README.md` | アプリの利用者・紹介を見る人 | 機能紹介、動作環境、ビルド手順、キーボードショートカット |
| `AGENTS.md` | コードを書く人・AI エージェント | 主要機能の箇条書き、設計方針、ディレクトリ構成ツリー、ビルド方法、コーディングルール |
| `learn/*.md` | コードを読んで学ぶ人 | レイヤーごとのファイル解説（責務・入力・出力・使用されている定数）、mermaid 図、データフロー |

## モードの選び方

- **差分モード（既定）**：ユーザーが範囲を言わなければこれ。対象の差分は次の順で決める。
  1. ユーザーがコミット・ブランチ・範囲を指定したらそれ（例：`git diff main...HEAD`、`git show <hash>`）
  2. 未コミットの変更があればそれ（`git diff HEAD` と未追跡ファイル）
  3. どちらもなければ、最後にドキュメントが更新されたコミット以降のコード変更（`git log -1 --format=%H -- README.md AGENTS.md learn` から `HEAD` まで）。範囲を決めたらユーザーに一言伝える。
- **全体モード**：「全部確認して」「ずれていないか全体を見て」などと言われたとき。ドキュメントの各記述をコードと照合する。時間がかかるので、learn/ はレイヤーごとに順に進め、進み具合を短く伝える。

## 差分モードの手順

1. **差分を読む**：`git diff --stat` で変わったファイルを見て、中身を読む。表示文字の大きさの調整のように、ドキュメントのどこにも書かれていない細かい変更しかなければ、「更新不要」と理由を添えて報告して終わる。何でも書き足せばよいわけではない。
2. **影響する箇所を探す**：下の「コードとドキュメントの対応」を手がかりにする。加えて、変わった識別子（クラス名・関数名・定数名・定数の値・ファイル名）を `README.md AGENTS.md learn/` から grep する。learn/ には定数の値（例：`REFILL_MAX_AMOUNT = 0.60`）や関数のシグネチャがそのまま書かれているので、grep で引っかかった箇所はコードの今の値と必ず突き合わせる。
3. **直す**：直し方は「書き方のルール」に従う。
4. **報告する**：直したファイルと、それぞれ何をなぜ直したかを短く箇条書きにする。判断に迷って直さなかった箇所があれば、それも書く。

## 書き方のルール

- **既存の形式に合わせる**。learn/ の各ファイル節は「責務 (Responsibility)／入力 (Input)／出力 (Output)／使用されている定数の名前 (Constants used)」の 4 項目でできている。新しいファイルの節を足すときも同じ形にして、節番号（2.1, 2.2 …）を振り直す。mermaid 図にクラスが増減したら図も直す。
- **書くのはコードで確かめたことだけ**。定数の値、関数名、引数はコードを開いて確認してから書く。
- **直すか聞くかの線引き**：コードを読めば正しい形が分かる食い違いは、迷わず直す。図の矢印が実際の呼び出し経路と違う、「完全撤廃」のような言い過ぎが実装と合わない、なども直す対象になる。ユーザーに聞くのは、変更の意図や設計の理由のように、コードからは読み取れないことだけにする。
- **同じ記述がほかにもある場合**：直した誤りと同じ表現がほかのドキュメント（AGENTS.md など）にもあれば、報告に書く。差分モードで範囲外なら、直すかどうかはユーザーに任せる。
- **消えたものは消す**。削除された機能・関数・定数の記述を「（廃止）」などとして残さない。ドキュメントは今のコードの姿だけを書く。
- **表記**：作品名は「Fude Sense」、識別子・ファイル名は `FudeSense`。「Fudesence」は誤りなので、見つけたら直す（ただし `kazuk/デスクトップ/Fudesence` のような他人の PC のパスは、次のリンクのルールで丸ごと消える）。
- **文体**：既存の文に合わせ、です・ます調で書く。README は利用者向けなので、内部の関数名より「何ができるか」を書く。learn/ は関数名・定数名を `` ` `` で囲んで具体的に書く。

## リンクのルール

learn/ のリンクの多くは `file:///c:/Users/kazuk/デスクトップ/Fudesence/...` という別の人の PC の絶対パスで、ほかの環境では開けない。**編集した learn ファイル**では、この形式のリンクをすべて、そのファイルから見た相対パスに直す。

- `file:///c:/Users/kazuk/デスクトップ/Fudesence/App/FudeCode/Views/CanvasView.h` → `../App/FudeCode/Views/CanvasView.h`
- `file:///c:/Users/kazuk/デスクトップ/Fudesence/learn/inputs.md`（learn/main.md 内）→ `inputs.md`
- `#L812` のような行番号アンカーは、今のコードでもその行が説明どおりの場所を指しているか確かめる。ずれていたら直し、確かめられなければアンカーを外す。

新しく足すリンクも最初から相対パスで書く。編集しないファイルのリンクまで直すのは全体モードのときだけにする（差分モードで関係ないファイルまで変えると、差分が読みにくくなるため）。

ただし、コードの変更で行が増減して、ドキュメントの行番号アンカーがずれることがある。差分モードでは、変わったコードファイルを指すアンカーを grep で探す。ずれていたら、そのドキュメントは「編集するファイル」として扱い、アンカーを直すとともに、そのファイルのリンクも相対パスに直す。中身の説明を直す必要がなくても、この扱いは同じ。

## やらないこと

- **コミットしない**。ドキュメントの変更は作業ツリーに残し、コミットするかはユーザーに任せる。
- **コードは変えない**。ドキュメントとコードが食い違っていて、コードのほうが間違っていそうなときも、コードは直さずに報告だけする。
